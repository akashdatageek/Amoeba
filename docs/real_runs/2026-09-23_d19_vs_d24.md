## What it shows

1. **d24 makes the Planner name what it lacks.** Final capability requests per draft went from 0.3 → 3.8 (flash-lite)
   and 0.9 → 5.1 (3.5-flash). On `db-choice`, which needs web search and a database sandbox, every d24 draft requested
   them: 4.3 and 9.0 per draft. d19 managed 0.3 and 1.3. The names still vary ("Web Search", "Web Research",
   "Market Research Tool"), so a later phase must merge them.
2. **The roles and steps now carry the detail, and the arithmetic is written down.** In both models, 100% of d24
   roles have goal, skills, outputs, success criteria and a prompt, against 0% for d19. Every d24 draft covers every
   requirement id with a step and a role. The derived numbers were correct in 9/9 (flash-lite) and 7/9 (3.5-flash)
   d24 drafts, against 6/9 and 6/9 for d19. d19 never computed the clickstream storage (0/6); d24 on flash-lite did
   (3/3).
3. **d24 converges; d19 never does.** Consensus: 7/9 and 9/9 for d24, 0/9 and 1/7 for d19, which always ran all 3
   rounds. Fewer rounds pay for the longer replies: flash-lite cost about the same per draft (18.9k vs 18.6k tokens),
   and 3.5-flash cost less with d24 (25.2k vs 29.9k).
4. **But the observers approve too easily.** Only 1/9 and 3/9 d24 drafts have a verification step done by a role
   other than the one that produced the work. Most "cross-verification" steps are done by the same specialists. The
   summariser check failed in 2/9 in each model. The observers approved these drafts anyway, so APPROVE is not yet a
   quality signal. `draft_quality` catches what they miss, and it is recorded but does not reject yet.
5. **The model matters less than the prompts here.** Within a prompt set, flash-lite and 3.5-flash differ less than
   d19 and d24 differ within a model. 3.5-flash's d24 drafts are longer (4.7 steps, 9 requests on db-choice), and its
   d19 drafts are no better at requesting tools.

## Caveats

- **3.5-flash d19 is partly confounded by cut-off replies.** 17 of its observer replies stopped at the 2048-token
  limit (d24: 1) while reporting only 78–603 output tokens. The model's hidden reasoning appears to count against
  `max_tokens`. Those replies are shorter than intended, which may have cost d19 consensus on that model. The next
  run should give observers of a thinking model more room (e.g. 8192).
- **2 d19 drafts on 3.5-flash failed on a third copied-parser limit.** The model put each role in its own
  ```` ```json ```` block, and `parse_sections` keeps only the first fenced block of a section (common.py:53), so 3 of
  the 4 roles were lost ("roster size 1"). This is the same class as D22; a fix is proposed as D26 and not applied.
- **The derived-number check is a string match.** One 3.5-flash d24 draft computed in binary units (57.22 GiB/day,
  20.39 TiB/year), which is defensible but scored as wrong. The d24 rate is therefore a slight undercount.
- **Coverage is self-reported.** `requirements_covered` checks the planner's own `covers` lines, not whether the step
  would really meet the requirement.
- 9 drafts per cell is small. Differences of one or two drafts are noise.

## Next

D26 (read every fenced block in a section); more observer room for thinking models; normalise capability names;
make observers check for an independent verification step (or let `draft_quality` send the draft back); then the
same comparison through Box 3, to see whether the richer drafts produce better answers.
