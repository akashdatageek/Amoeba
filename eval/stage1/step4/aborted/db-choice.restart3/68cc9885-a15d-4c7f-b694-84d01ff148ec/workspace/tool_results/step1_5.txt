Transactions benchmark • \u0007 MongoDB without using transactions runs on the equivalent of READ UNCOMMITTED isolation mode. This allows phenomena like non-consistent reads, skipped documents on a query or reading data that is not durable to happen. Avoiding these inconsistencies puts significant burden on the application developer. • \u0007 MongoDB with transactions offers SERIALIZABLE isolation guarantees. PostgreSQL has been tested both with READ COMMITTED and SERIALIZABLE isolation levels. MongoDB was found to be one order of magnitude (4x-15x) slower than PostgreSQL on READ COMMITTED; or 4-14x slower compared to PostgreSQL on SERIALIZABLE – when comparing exactly the same level of isolation guarantees provided. PostgreSQL SERIALIZABLE is a bit slower than READ COMMITTED, but not by much. PostgreSQL processes more than 20 thousand transactions per second when MongoDB doesn’t reach 2 thousand. PERFORMANCE BENCHMARK POSTGRESQL / MONGODB 6/46 • \u0007 PostgreSQL latencies are under 50ms for the 99% percentile, and as low as less than 1 millisecond. OLTP Benchmark • \u0007 PostgreSQL performance depends heavily on the number of concurrent users (connections). When tuned for the optimal number of connections, it performs very well, but performance drops if it is overwhelmed with connections. PgBouncer or some other similar connection pooler is recommended. In this case, PostgreSQL performance is stable close to the maximum performance. This is a recommended pattern in production. • \u0007 For the XL test (2TB database, doesn’t fit in memory), PostgreSQL outperforms MongoDB in every scenario. If PgBouncer is used, it is between 25x-40x times faster. • \u0007 For the in-memory test (4GB database, fits in memory), PostgreSQL outperforms MongoDB by a factor of 2-3x. This applies both to XFS and ZFS filesystems. \u0007 If PostgreSQL is run without PgBouncer, then it is only faster than MongoDB when used under the optimal number of concurrent users, but this is not recommended.
